# 2. Plugins, and how daukle gets them

daukle has no languages in it. **Every ability you use is a plugin**, and this page is about where
plugins come from, how they are pinned, and how to write one.

The example on this page is `daukle-local-plugin`, in this repository.

## The three ways to name a plugin

```toml
[plugins]
# a published coordinate, resolved through a resolver
npm = { resolver = "github", coordinate = "daukle/npm@^1.0.0" }

# a url and the digest of the bytes it must serve
npm = { url = "https://.../plugin.lua", sha256 = "..." }

# a path inside your project, for a plugin you are writing
banner = "./plugins/banner.lua"
```

**A coordinate still ends in a digest.** The resolver asks the forge which release matches the
range, and what comes back is fetched and checked. There is no unpinned form of any acquisition in
daukle and no flag that relaxes one.

That is worth stating plainly because it is the property everything else rests on: **a build that
succeeded once succeeds the same way forever, or it fails loudly.** The one exception is a
deliberate resolve, and page 4 covers it.

## Depending on part of a plugin

**A plugin may ship MODULES, and a project names the ones it loads.** Since `daukle 0.9.0` a
`[plugins]` entry takes `modules`:

```toml
[plugins]
# only the dependency writer, and only its grant
cmake = { resolver = "github", coordinate = "daukle/cmake@^1", modules = ["deps"] }
```

```toml
[plugins]
# the toolchain AND the dependency writer
cmake = { resolver = "github", coordinate = "daukle/cmake@^1", modules = ["main", "deps"] }
```

**Each module declares its own `daukle.plugin{}`, so each carries its own `uses` and `env`**, and
depending on one never grants what another needs: the line above that names only `deps` gets
`region` and not the toolchain's `exec`. `"main"` is the plugin's `plugin.lua`; any other name is
`modules/<name>.lua` inside the plugin's published archive. **With no `modules` key, only
`plugin.lua` loads**, exactly as before. The artifact is fetched and checked once, however many of
its modules the line names, and `config print` shows a row per module as `<label>/<module>`, which
`daukle plugin update` also accepts. A `requires` override on the line reaches whichever named module
declares that alias, and one that no named module declares is refused by name.

**Since `daukle 0.9.1`**, a module the plugin does not carry is refused naming the line and the
modules it does carry. A name is matched exactly, case included, and two names on one line that
differ only in case are refused. A plugin that carries a `modules/main.lua` is refused too, because
`"main"` always means `plugin.lua` and that file could never load, and a `[plugins]` key may not
contain `/`.

## Writing one

A plugin is a Lua file. This is a complete one:

```lua file=examples/daukle-local-plugin/plugins/banner.lua
-- A whole plugin. It declares one toolchain, and that toolchain generates one
-- file from the manifest.
--
-- daukle.plugin MUST be the first call in the chunk: the pre-pass that reads
-- "uses" runs before anything else, and a daukle.require above this line is
-- refused rather than silently allowed.
daukle.plugin{ api = 1, uses = {} }

daukle.toolchain{
  name = "banner",
  -- generate is a PURE function of the manifest. It may not call exec or tool,
  -- because "daukle check" runs it and check must never start your compiler.
  -- It returns a table of relative path to file text, and daukle does every
  -- write, which is why the sandbox has no write verb at all.
  generate = function(context)
    -- In generate the block is context.config; in a TASK the same block is
    -- context.toolchain.config. Real plugins keep a one line config_of helper
    -- so the two cannot be confused.
    local config = context.config
    local greeting = config.greeting or "hello"
    local lines = {
      "/* Generated by the banner toolchain. Do not edit. */",
      '#define BANNER "' .. greeting .. ' from ' .. context.project .. '"',
      '#define BANNER_VERSION "' .. context.version .. '"',
    }
    return { ["banner.h"] = table.concat(lines, "\n") .. "\n" }
  end,
}
```

And the manifest that uses it:

```toml file=examples/daukle-local-plugin/daukle.toml
schema = 1
project = "daukle/example-local-plugin"
version = "3.1.4"

[modules]

# A plugin can be a LOCAL PATH while you are writing it. The same plugin is
# published by giving it a coordinate instead; nothing in the plugin changes.
[plugins]
banner = "./plugins/banner.lua"

[toolchains.banner]
greeting = "good morning"
```

`daukle sync` writes `build/daukle/banner/banner.h`:

```
/* Generated by the banner toolchain. Do not edit. */
#define BANNER "good morning from example/your-own-plugin"
#define BANNER_VERSION "3.1.4"
```

## What `uses` is for

`uses = {}` above means the plugin asks for no host capability at all. A plugin that needs to run
a program declares `uses = { "exec", "tool" }`, one that fetches declares `"fetch"`, and so on.

**It is a statement a reader of your manifest can act on.** A plugin that did not declare `exec`
cannot start a process, and the refusal comes from daukle rather than from the plugin's good
intentions. When you review a dependency's plugin, `uses` is the line to read first.

**`exec` and `provision` are also withheld by WHEN, whatever `uses` says.** One `plugin.lua` may
declare a source or a language beside a toolchain or a publisher, so a GitHub plugin can both
fetch a manifest and publish a release. But a source's `load` and a language's `apply` run on every
command, often for a dependency you did not write, so neither may start a process or provision a
tool: the call is refused naming the phase, `daukle.exec is not available while a source loads`.
Call them from a task or a publish callback. A chunk's top level and a toolchain's `generate` are
refused the same way. **A resolver may not declare either at all**, because it is acquired before
any pin exists. A chunk that declares a source or a language beside `exec` or `provision` needs
`api = 2`, which `daukle 0.8.0` is the first to provide.

**And anywhere else, too: since `daukle 0.8.1` the two verbs run ONLY inside a task's `run` or a
publisher's `publish`.** The named refusals above come first because they tell you which phase you
are in; beneath them, any call from outside those two callbacks is refused with `daukle.exec is
available only inside a task or publish callback`. **A plugin may not set a `__gc` finalizer**
either, since one runs at whatever moment Lua collects garbage, outside every callback:
`setmetatable` refuses a metatable carrying `__gc`, and since `daukle 0.9.1` so does the one in the
project's own `daukle.lua`. `__close` is unaffected, because a to-be-closed variable runs at scope
exit, inside the callback that declared it.

## What `api` is for, and when to raise it

`api = 1` says which plugin api your plugin was written against. **daukle refuses an api HIGHER
than it provides, by name and with its own version in the message**, so a plugin needing something
newer than the daukle running it says so instead of misbehaving:

```
plugin "gradle": needs daukle api 2 and this daukle 0.7.0 provides 1, so upgrade daukle
```

**A LOWER api is accepted forever.** A plugin declaring `api = 1` keeps working on every later
daukle, so there is no reason to raise yours to match a newer release. Raise it only when your
plugin genuinely needs a capability that an older daukle lacks.

**Most new capabilities need no api bump at all, because `uses` already polices them.** A verb that
a daukle does not have is refused by name the moment the plugin is declared, which every daukle
back to `0.1.0` does. The api number exists for the capability shape that has no signal of its
own: **a new field inside a context table your callback already receives**, which an older daukle
simply leaves absent.

**Declare the LOWEST api your plugin actually needs.** Declaring a higher one refuses daukles that
would have run your plugin perfectly well.

## What the sandbox gives a plugin

`string`, `table`, `math`, and the handful of base functions. **Not** `io`, `os`, `require`,
`load` or `debug`. A plugin cannot read your home directory, and a `daukle check` on a repository
you just cloned cannot start a process.

Two consequences surprise people, so they are worth saying now:

- **There is no `print`.** A plugin reports by writing a file or by failing with a message.
- **There is no `pcall`.** A plugin cannot catch a failed fetch and carry on, so a network failure
  fails the task. That is usually the right answer anyway.

## `daukle.manifest`, for a plugin that declares a task per project entry

A plugin's task list is usually fixed, because `javac` has a fixed set of things to do. A plugin
driving a tool whose task list the PROJECT extends is different: a CMake project has its own
targets, a package has its own scripts. Such a plugin reads the manifest when it loads and calls
`daukle.task` once per entry.

`daukle.manifest` is the manifest's file name, so the plugin never writes one of its own:

```lua
daukle.plugin{ api = 1, uses = { "read", "parse" } }

daukle.toolchain{ name = "demo", generate = function() return {} end }

local config = daukle.parse(daukle.read(daukle.manifest), daukle.manifest)
local scripts = config.toolchains and config.toolchains.demo and config.toolchains.demo.scripts
for name in pairs(scripts or {}) do
  daukle.task{ name = "demo:" .. name, run = function() ... end }
end
```

**Write `"daukle.toml"` instead and you have made that spelling a requirement of every project
your plugin serves**, because a manifest passed to `daukle sync <path>` under any other name then
fails before anything runs.

Three things to know:

- **It names the PRIMARY manifest**, so a `daukle.lua` overlay's additions are not visible here: a
  chunk loads before overlays are applied. Declare what the tasks come from in the primary file.
- **A task name is lowercase**, with digits, `.`, `_` and `-`. A tool's own `publishGithub` has to
  be spelled `publish-github`.
- **A duplicate name is fatal to the whole project**, not just to that task, so refuse a collision
  where the entries are written.

## Where generated files go

**`build/daukle/<toolchain>/` is derived**: `daukle clean` deletes it, and it is gitignored. That
is where a generated header, a generated `build.gradle` or a tool's scratch output belongs.

**`daukle/<toolchain>/` is committed**: it is for what a resolve produced and a clone must carry.
Page 4 is the one place it appears.

**Nothing a plugin generates goes at the project root.** The rule is simple: if the user is not
supposed to edit it, it does not sit where the user works.
